# Statnive v1.0.0 — E2E Acceptance Checklist

Run on a real WooCommerce site (HPOS preferred). Tick each row before tagging v1.0.0. Last-good baseline result lives in the PR description.

## Smoke (pre-merge)

- [ ] Activate the plugin on a WC-absent site → no fatal, Statnive menu visible (Capability fallback works).
- [ ] Activate the plugin on a WC + HPOS site → no fatal, HPOS compat declared at `before_woocommerce_init`.
- [ ] All 3 admin submenus render: `Overview` / `Revenue Report` / `Settings`.
- [ ] First submenu reuses the parent slug — no duplicate "Statnive" label in sidebar.
- [ ] The in-app horizontal nav shows a Revenue tab with the DollarSign icon between Real-time and Settings.
- [ ] Console: 0 errors on first load of each of the 3 submenus.
- [ ] `window.StatniveDashboard.currency` populated from `get_woocommerce_currency()`.
- [ ] `window.StatniveDashboard.initialRoute` matches the active `?page=` slug.

## Capability + REST

- [ ] Administrator (no WC) sees the Statnive menu (fallback to `manage_options`).
- [ ] Administrator on a WC site sees the menu (cap chain hits `view_woocommerce_reports`).
- [ ] Shop Manager on a WC site sees the menu (cap chain hits `view_woocommerce_reports`).
- [ ] Subscriber (no eligible cap) does NOT see the menu and gets 403 on every `/statnive/v1/revenue/*` endpoint.
- [ ] All 10 REST endpoints return 200 for authenticated admin:
  - `GET /statnive/v1/revenue/wc-status`
  - `GET /statnive/v1/revenue/summary?from&to`
  - `GET /statnive/v1/revenue/timeseries?from&to`
  - `GET /statnive/v1/revenue/by-channel?from&to`
  - `GET /statnive/v1/revenue/by-utm?from&to[&limit]`
  - `GET /statnive/v1/revenue/by-landing?from&to[&limit]`
  - `GET /statnive/v1/revenue/products?from&to[&limit]`
  - `GET /statnive/v1/revenue/funnel?from&to`
  - `GET /statnive/v1/revenue/coupons?from&to[&limit]`
  - `GET /statnive/v1/revenue/refunds?from&to`
- [ ] Each response carries `meta.request_id`, `meta.currency`, `meta.currency_minor_unit`, `meta.timezone`, `meta.generated_at`, and for ranged endpoints `meta.period`.
- [ ] Unauthenticated curl → 401 / 403.
- [ ] `statnive_view_reports_caps` filter changes the cap chain: e.g. `add_filter('statnive_view_reports_caps', fn() => ['manage_options']);` pins to admin-only and Shop Managers lose access.

## Order lifecycle (read-only against WC verified)

- [ ] Place a classic-checkout order → row appears in `wp_statnive_orders` keyed on `wc_order_id`.
- [ ] Same order via block checkout → row appears, same shape.
- [ ] Re-fire `woocommerce_order_status_completed` for an existing order → still ONE row in `wp_statnive_orders` (idempotent upsert).
- [ ] Admin-created order (`woocommerce_new_order`) → row created with `created_via='admin'`.
- [ ] REST API-created order → row created with `source_type=NULL` in attribution, `channel='Direct'`.
- [ ] BACS / cheque order stays in `on-hold` → row created, NOT counted in revenue summary.
- [ ] Order paid via Stripe → status flips to `processing`, summary picks it up.
- [ ] Cancel an order → status updates, summary excludes it.
- [ ] **NO writes** to `wp_posts`, `wp_postmeta`, or any `wp_wc_*` table during any of the above. Audit via `mysqldump` snapshot before+after.
- [ ] **NO new entries** in `wp_options` other than `statnive_*` keys.

## Attribution (WC 8.5+ Order Attribution)

- [ ] Visit site with `?utm_source=newsletter&utm_medium=email` then check out → `statnive_order_attribution` row has `channel='Email'`, `utm_source_lower='newsletter'`.
- [ ] Visit via `?utm_source=facebook&utm_medium=cpc` from a Facebook referrer → `channel='Paid Social'`.
- [ ] Visit via `?utm_source=google&utm_medium=cpc` → `channel='Paid Search'`.
- [ ] Visit from `chat.openai.com` → `channel='AI Assistants'`.
- [ ] Direct visit (no referrer, no UTM) → `channel='Direct'`, `source_type='typein'`.
- [ ] WC < 8.5 fallback (or attribution disabled) → row written with NULL fields, `channel='Direct'`.
- [ ] Renewal order (WC Subscriptions) — `created_via='subscription'` — attribution copied from parent.

## Items / coupons / refunds

- [ ] 1-item order → 1 row in `statnive_order_items` matching `wc_order_item_id`.
- [ ] Multi-coupon order (`WELCOME10` + `FREESHIP`) → 2 rows in `statnive_order_coupons`, each with correct `discount_amount` and matching `code_lower`.
- [ ] Same coupon in different cases (`Welcome10` vs `welcome10`) — Coupon Performance report groups them on `code_lower`.
- [ ] Full refund → 1 row in `statnive_order_refunds`, `orders.refund_total` matches refund amount, `orders.status` set to `refunded`.
- [ ] Partial refund → row written, `orders.refund_total` accumulates, `order_items.refund_quantity` + `refund_amount` distributed by `_refunded_item_id`.
- [ ] Refund amount stored as POSITIVE (not the WC negative line-item convention).
- [ ] Two partial refunds → 2 refund rows, `refund_total` is their sum.

## Funnel

- [ ] Visit a single-product page → `wc_product_view` event row in `statnive_events`.
- [ ] Add product to cart → `wc_add_to_cart` event row.
- [ ] Start checkout via classic shortcode → `wc_checkout_start` with `channel='classic'`.
- [ ] Start checkout via block checkout → `wc_checkout_start` with `channel='blocks'`.
- [ ] Funnel endpoint shows non-decreasing counts (view ≥ ATC ≥ checkout start ≥ purchase).
- [ ] Express checkout (Apple Pay / Google Pay) → `wc_purchase` recorded; `wc_checkout_start` skipped (documented limitation, no regression).

## Privacy + exclusions

- [ ] Order placed under DNT / GPC / declined consent → order row written, attribution row has `source_type=NULL`, channel='Direct'. Revenue still counted. (Revenue ≠ attribution.)
- [ ] `add_filter('statnive_should_track', '__return_false')` → no order rows, no event rows (full opt-out per request).
- [ ] Order placed by a user with an excluded role (Settings → Exclusions) → not captured.
- [ ] WP Tools → Export Personal Data with the customer email → returns matching `statnive_orders` rows. (Privacy Exporter — PR 4/5 wiring still pending integration into WP exporter; if not yet wired, mark this row as v1.x.)
- [ ] WP Tools → Erase Personal Data → nulls `customer_email_hash` + `customer_user_id`, retains aggregate revenue. (Same caveat as above.)
